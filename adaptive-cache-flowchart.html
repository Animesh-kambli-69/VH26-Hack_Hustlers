1 System layout — where the cache engine slots in

Read calls flow down the spine. The cache wraps services, never routes/controllers, so layers stay clean.

React SPA (React Router) — client/src/App.jsx routes NEW
/ Home (catalog + search + sort) · /products/:id Product (detail + related) · /cart · /checkout · /orders · /wishlist — plus /admin/cache-dashboard CacheDashboard page (Recharts + SSE). All fetching via one file: api/client.js.
Vite dev proxy — client/vite.config.js
forwards every /api/* request to the Express API at 127.0.0.1:3001 (same-origin, no CORS).
Express app — server/src/app.js + index.js
JSON body parser · morgan logging · GET /api/health · mounts 3 routers (/api/products, /api/categories, /api/orders) · central error handler → 404 handler.
Routes (thin) — routes/products.js · categories.js · orders.js NEW
URL → controller mapping only, plus a new routes/cache.js mounted at /api/cache: GET /stats · POST /config · GET /stream (SSE) · POST /simulate.
Controllers (thin) — controllers/productController.js · orderController.js
Parse the request (req.query, req.params, req.body), call one service function, shape the JSON. No business logic → untouched by Phase 2.
🧠 Adaptive Cache Engine — services/cache/ (all new) NEW CACHE_INSERTION_POINT
Wraps every read service function with cache.get(key) → hit? serve : compute + cache.set(key, value, meta). Inside the engine:
  • Utility Engine — scores every entry: U = ((Ĉlat·wL + Ĉ$·wM)·log(1+F)) / S · e−λΔt
  • Store + min-heap (lazy deletion) — re-pick eviction victim in O(log N), never O(N)
  • Policies — adaptive (default) · lru · lfu · gdsf · no-cache, switchable live via env CACHE_MODE
  • Admission filter (S3-FIFO style) — reject one-hit wonders; keeps cold-start clean
  • Single-flight lock — one compute per concurrent duplicate miss (checkout spike)
  • Cost Advisor (costAdvisor.js) — simulated auto-scaler ROI, emits a recommendation
  • Eviction events → published to /api/cache/stream (dashboard feed)
Services (business rules — the functions the cache wraps)
productService.js: listProducts · getProduct · listCategories · decrementStock · restock  |  orderService.js: createOrder · quoteOrder · listOrders · getOrder · cancelOrder · advanceOrderStatus
Data layer
data/products.js — 15 in-memory products, 5 categories  ·  db/fileDb.js — JSON-file order store (demo-only, swap for a real DB before scaling)  ·  data/promoCodes.js — server-side promo truth
📌 How to read this repo vs the PRD:
  • The PRD's categoryService.js does not exist yet — category listing lives in productService.listCategories (routes/categories.js → productController). Wrap the real function.
  • "Detail + related" is two HTTP calls today: GET /api/products/:id and a second GET /api/products?category=… fired by ProductPage.jsx. The 80–150 ms "related-products computation" is a Phase-2 model, not current server work.
  • The PRD's phase-1 stack says Express 4 / Vite 5; the repo currently resolves express ^5 and vite ^8. Cosmetic drift — the cache design is unaffected.

2 Read path — what the cache does on every GET

Same skeleton for catalog, detail, categories and order history — only the key, cost metadata and TTL change (see panel 5).

Request arrives, e.g. GET /api/products?search=iphone&sort=price-asc or GET /api/products/1
1 · Build the cache key service entry fn
  • products:list:{category}:{search}:{sort} — one entry per distinct query shape
  • product:detail:{id} · categories:list · orders:customer:{customerId}
2 · cache.get(key) — is it in the store and not TTL-expired?
Every lookup also bumps bookkeeping in O(1): freq = freq·0.99 + 1 (decayed frequency, stops hot keys from exploding the score) and refreshes lastAccess. Utility is re-derived lazily via the heap, not a full scan — total overhead target < 2 ms.
✅ HIT
  • Serve the stored payload (≈5 ms)
  • Record metric: hit, latency saved = costLatency, ₹ saved
  • Heap re-ranks the entry upward (it got hotter)
❌ MISS (or expired)
  • 3 · Take the single-flight lock for this key (duplicates share one compute)
  • 4 · Run the real service fn — e.g. productService.listProducts scans/filters/sorts, or orderService.listOrders reads fileDb
  • 5 · Admission filter: worth caching? First-timers / one-hit-wonder searches are skipped (cold-start scenario stays clean)
6 · cache.set(key, value, meta) — admit the entry miss path only
  • Entry = { key, value, sizeMB, costLatency, costMoney, freq, lastAccess, type, utility, expiresAt }
  • While inserting: if total > capacity, pop the min-utility victim off the heap → eviction event {key, U, type, sizeMB, cost} → SSE stream
  • Adaptive keeps expensive entries (SEARCH/DETAIL/ORDER) and evicts cheap CATALOG first — LRU/LFU evict purely by recency/frequency and drop the expensive ones.
Respond to the client — and stream one metric line to the dashboard
hit/miss per policy, latency saved (s), ₹ saved (×83), P99 sample (hit ? 5ms : costLatency), memory by type → GET /api/cache/stream (SSE).

3 Write path — checkout never hits cache, but it pulls the trigger on invalidation

POST /api/orders is the most expensive call (~400–800 ms model) and mutates stock, so it is deliberately not cached — it invalidates.

CheckoutPage → api.createOrder({ customerId, customer, items, shippingMethod, promoCode })
orderService.createOrder — the 6 steps (unchanged from Phase 1)
  1. validate customer (name / email)
  2. resolve items — each productId looked up via productService.getProduct, qty validated
  3. stock check on every line → 409 if short
  4. decrementStock(id, qty) — in-memory Map overlay in productService
  5. server-side pricing — shipping method + promo codes (computePricing), client prices never trusted
  6. fileDb.push(order) → order ORD-… with events history, status confirmed
🔥 Invalidate — cache.invalidate(pattern) NEW — the consistency half of the engine
  • products:list:* — stock numbers changed, every catalog/search listing is stale
  • product:detail:{each purchased productId}
  • orders:customer:{customerId} — order history changed
  • categories:list — only if a product's stock hit 0 (PRD rule; catalog is static otherwise)
Other mutators re-use the same hook: cancelOrder (restocks → same product keys) and advanceOrderStatus (order state changed → orders:customer:*, orders:id:*). quoteOrder is side-effect-free and stays uncached (prices must stay server-truth).
201 { order } → OrderSuccessPage — then GET /api/orders/:id and GET /api/orders?customerId=… re-read fresh from the cache (just invalidated, so they recompute once, then re-cache).

4 Observability loop — simulator, SSE stream, dashboard

All of this is for demo/benchmark, never real shoppers. Requests come from a workload generator, metrics come back over SSE.

Dashboard controls → POST /api/cache/config + POST /api/cache/simulate
  • Scenario: Normal · BBD Spike · Diwali→Christmas Shift · Cold Start
  • Weight sliders: wL (latency), wM (money), λ (recency decay) — applied live, no restart
  • Capacity 10–150 MB · req/s 50–1000
Workload Generator — services/cache/workloadGenerator.js (new)
  • Zipfian key popularity (α≈1.2 → 20% of products get 80% of views) + Poisson arrivals
  • Traffic mix: 60% browsing · 20% search · 15% detail · 5% checkout
  • BBD Spike = 10× burst aimed at iPhone (product:detail:1 + search=iphone) — 70% expensive keys, the exact case where LRU drops the wrong entries
  • Generated requests re-enter the read path (panel 2) and are metered per policy
Cache engine → GET /api/cache/stream — SSE pushes JSON metric frames every tick
Adaptive and LRU/LFU/GDSF/No-Cache all run side-by-side on the same synthetic traffic so the dashboard can compare them honestly.
CacheDashboard.jsx — /admin/cache-dashboard (Recharts; route added in App.jsx)
  • Hit-rate % — Adaptive vs LRU vs LFU vs GDSF vs No-Cache. Adaptive should pull ahead during the BBD spike
  • ₹ / latency saved — cumulative, $ → ₹ ×83, e.g. "₹7.2L/month per 50MB node"
  • Memory by type — stacked bars: CATALOG cyan · SEARCH amber · DETAIL purple · ORDER orange — Adaptive should look purple/amber, LRU mostly cyan
  • Eviction feed — {key, U, type, sizeMB, cost}; watch cheap CATALOG leave before expensive SEARCH/DETAIL
  • P99 latency — hit ? 5ms : costLatency; No-Cache/LRU spike to ~2.2 s under BBD while Adaptive holds ~85 ms
  • Cost Advisor card — preventableMisses × avgCost > cost of +100MB node → "SCALE_UP, ROI ≈ 80×". Advisory only, no real scaling

Utility at a glance (§1.2 of the PRD) — why the engine evicts the way it does: CATALOG U≈0.12 → evicted first (cheap to rebuild, cyan bars leave) · ORDER U≈0.18 · SEARCH U≈0.35 · DETAIL U≈0.45 → kept (purple/amber bars stay) · expensive CHECKOUT-style results U≈0.70 → held longest. LRU has no idea a ₹2 recommendation is costlier to rebuild than a ₹0.001 catalog row — that's the whole pitch.
* The 80–150 ms "related products" recompute is the PRD's model for Phase 2; today related items are a second client call (panel 1 note).
